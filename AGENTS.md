# AGENTS.md

## Project overview

`cordn-rs` is a native Rust port of the TypeScript `cordn` MLS delivery
coordinator — a ContextVM/MCP server that stores and delivers MLS key packages,
welcomes, join requests, and per-group opaque message streams.

Primary implementation areas (target layout):

- `crates/cordn-core/src/` — core delivery-service state and behavior
  - `types.rs` — domain records (port of `references/cordn/src/coordinator/types.ts`)
  - `storage/` — `CoordinatorStorage` trait, `in_memory.rs`, `sqlite.rs`
  - `coordinator.rs` — core logic + pub/sub
  - `mls_parse.rs` — minimal key-package reader (credential identity +
    last-resort extension detection; ports `lastResortKeyPackage.ts`)
  - `ratelimit.rs` — token-bucket rate limiter
  - `contracts.rs` — serde wire types (port of
    `references/cordn/src/contracts/index.ts`); derives `schemars::JsonSchema`
    under the `schemars` feature for rmcp tool schemas
- `crates/cordn-server/src/` — ContextVM server bindings and runnable entrypoint.
  The rmcp/transport deps are gated behind the `server` feature so the
  rmcp-free `adapter` + `config` build and test without the full `contextvm-sdk`
  (`cargo build -p cordn-server --features server` for the bin).
  - `adapter.rs` — `CoordinatorAdapter` (rate limit, quota, identity binding,
    MLS admission, output mapping, streaming loops) — rmcp-free + unit-tested
  - `methods.rs` — rmcp `#[tool]` glue (`CordnServer`) extracting
    `ClientPubkey` / `OpenStreamWriter` from `RequestContext`
  - `config.rs` — env config (port of `runtimeConfig.ts`)
  - `main.rs` — bin entrypoint (signer, sqlite/memory storage, transport, banner)
- `references/cordn/scripts/gen_key_packages.test.ts` — regenerates the
  `ts-mls` parser fixtures into `crates/cordn-core/tests/fixtures/`

The TypeScript coordinator under `references/cordn/` (currently `0.5.1`) is the
**parity source of truth**. Behavior, wire shapes, the SQLite schema, and the
test coverage are all ported from it. `references/` trees are read-only.

## Architectural decisions (locked)

These are settled. Do not relitigate them without an explicit change request.

1. **Minimal MLS parser at runtime, not `openmls`.** The `mls_parse` module
   reads key packages only to (a) verify they decode, (b) read the
   BasicCredential identity, (c) detect the last-resort extension. It is
   hand-rolled, ported from `references/cordn/src/lastResortKeyPackage.ts`, and
   cross-checked against captured `ts-mls` fixtures in tests. `openmls` is
   **not** a dependency (neither runtime nor dev). The coordinator is opaque to
   MLS payload contents by spec mandate (`references/cordn/spec/00.md` §7-8).

   **Where the parsing happens:** the **coordinator core does not parse MLS**.
   `Coordinator::publish_key_package` receives `is_last_resort` already computed
   by the caller. The parser is used by the **adapter** (`cordn-server`) at
   publish time to verify-decode, read the credential identity (for the binding
   check), and compute `is_last_resort`. This keeps `cordn-core` MLS-free at the
   coordinator layer; the parser itself still lives in `cordn-core`
   (`src/mls_parse.rs`) as a leaf module so it is independently testable.

   **Fixture strategy (diverges from the original "openmls dev-dep" idea):**
   parser tests cross-check against real key packages generated by `ts-mls`
   (the same library the TS coordinator encodes with) via
   `references/cordn/scripts/gen_key_packages.test.ts`, captured into
   `crates/cordn-core/tests/fixtures/key_packages.json`. This is simpler than an
   `openmls` dev-dependency and gives **stronger** parity evidence (exact
   production wire bytes + `ts-mls`'s own `isLastResort` answer). Regenerate
   with `npx vitest run scripts/gen_key_packages.test.ts` from
   `references/cordn`.

   **Wire-format note:** `ts-mls` uses its **own variable-length integer** for
   every length prefix (top 2 bits of the first byte → 1/2/4-byte field), NOT
   RFC 9420's fixed-width per-field prefixes. `read_var_bytes` implements this
   single scheme and is the only length decoder the parser needs.

2. **Store raw MLS bytes, never re-encode.** Key packages, welcomes, and group
   messages are stored as the exact incoming wire bytes. The TS code does an
   wasteful `encode(decode(...))` round-trip; we do not. This is simpler, more
   spec-correct ("store verbatim"), and eliminates any encode-parity risk
   between Rust and TS.

3. **`openmls` is a `dev-dependency` only** — used to generate realistic MLS
   fixtures (key packages, welcomes, group messages) in Rust unit/integration
   tests. It also cross-validates the minimal runtime parser.

4. **Two-crate workspace**: `cordn-core` (lib, no network deps) + `cordn-server`
   (bin, pulls in `contextvm-sdk` + `rmcp` + `tokio`). Do not split further
   (no separate `cordn-storage` / `cordn-contracts`) unless a real need appears.

5. **`rusqlite`, not `sqlx`.** The coordinator is single-writer synchronous by
   design contract; `rusqlite` mirrors the TS `better-sqlite3` model and the
   schema maps 1:1. Async SQL adds machinery for zero benefit here.

6. **Async runtime is `tokio`.** The coordinator core is async because pub/sub
   and the server layer are. Storage ops (sync, fast) are called inline from the
   async context; reach for `spawn_blocking` only if a measurable stall appears.

7. **Pub/sub via `tokio::sync::mpsc`**, not `broadcast`. Per-subscriber,
   per-group cursor dedup does not map cleanly onto broadcast. Port the TS
   `subscribeGroupMessages` / `subscribeManyGroupMessages` backlog-replay-then-
   live logic line-for-line (see Coordinator contract notes below).

8. **`now()` injection** for deterministic clocks (port the TS `now` option). All
   timestamps and per-group cursor allocation go through the injected clock.

9. **Cleanup timer** is a tokio task with a `CancellationToken`, aborted on
   `Coordinator::close()`. This replaces the TS `setInterval(...).unref()`.

10. **Polyglot monorepo is a separate, later effort.** Do not restructure this
    repo to host the TS implementation. The 2-crate Rust workspace is
    forward-compatible with becoming a subtree of a future polyglot monorepo.

### Resolved: `contextvm-sdk` client-pubkey injection

The TS adapter reads the injected caller pubkey and request-event id from
`extra._meta`. `contextvm-sdk` provides the Rust
equivalent: the rmcp worker injects a `ClientPubkey` wrapper into request
`extensions` (re-exported from `contextvm_sdk::transport::server`), and the
inbound Nostr event id is available as the rmcp request id (`ctx.id`, since the
worker rewrites the request id to the event id). The adapter (step 5) reads
`ctx.extensions.get::<ClientPubkey>()` and `ctx.id`, and retrieves the
`OpenStreamWriter` from extensions for streaming tools. Shipped as
`contextvm-sdk` 0.2.1 on crates.io; `cordn-server` depends on it by version.

### Resolved: inbound publication Nostr event (`InboundEvent`)

The contextvm-sdk worker injects `ClientPubkey` (the SDK-verified signer) and
the full inbound client-signed request event
as `InboundEvent(pub nostr::Event)` in request `extensions` (re-exported from
`contextvm_sdk::transport::server`). For gift-wrapped requests this is the inner,
signature-verified event (its `pubkey` equals `ClientPubkey`); for plaintext it
is the outer event. Synthetic transport-internal requests carry no event.

`methods.rs::publication_event` extracts it and converts it to our wire
`NostrEvent` via a JSON round-trip (both use the canonical Nostr event shape),
then hands `Some(event)` to `CoordinatorAdapter::publish_key_package`, which runs
the full TS binding (`event.pubkey == client_pubkey == key-package credential
identity`) and stores the real event (with its client `sig`) so `consume` returns
it. `None` (synthetic-only) yields `MissingPublicationEvent`. The earlier
synthetic empty-`id`/`sig` fallback is gone — it broke the TS client's `min(1)`
Zod validation on consume, and `sig` could never be reconstructed server-side
anyway (the server lacks the client's private key).

Shipped as part of `contextvm-sdk` 0.2.1 on crates.io (the former
`feat/clientPubkey` branch, merged and released).

```bash
cargo build                  # build workspace

cargo check                  # fast type-check

```

## Development workflow

- Build: `cargo build`
- Run the coordinator server: `cargo run -p cordn-server`
- Type-check without codegen: `cargo check --all-targets`
- Format before committing: `cargo fmt --all`
- Lint: `cargo clippy --all-targets -- -D warnings`

Environment notes (server, ported from `references/cordn/src/server/runtimeConfig.ts`):
the server loads `.env` then `.env.local` (first-write-wins per key). Relevant
variables include `CORDN_SERVER_PRIVATE_KEY`, `CORDN_RELAY_URLS`,
`CORDN_SERVER_NAME`, `CORDN_SERVER_ABOUT`, `CORDN_SERVER_WEBSITE`,
`CORDN_ANNOUNCED`, `CORDN_STORAGE_BACKEND` (`memory` | `sqlite`),
`CORDN_SQLITE_PATH`, `CORDN_MAX_AGE_DAYS`, and the `CORDN_RATE_LIMIT_*` and
`CORDN_MAX_*_KEY_PACKAGES_*` abuse-protection knobs.

## Testing instructions

Four layers — all four are required for the drop-in guarantee.

1. **Unit tests** (`#[cfg(test)] mod tests` per module, or `tests/` integration
   tests). Fast, pure Rust. Storage tests use byte fixtures.
2. **Rust integration tests** with `openmls` fixtures — realistic key packages,
   welcomes, and group messages generated in-process. Port coverage from
   `references/cordn/src/coordinator/coordinator.test.ts`,
   `coordinator.integration.test.ts`, and `storage/storage.test.ts`.
3. **Cross-impl smoke**: run `cordn-server` and point the TS CLI client
   (`references/cordn`, `pnpm run client:cli`) at it. This is the gold-standard
   wire-shape parity check.
4. **DB cross-read parity**: a database written by the TS coordinator must be
   readable by `cordn-rs`, and vice-versa. This is the literal proof of the
   drop-in guarantee. The TS→Rust direction is covered by
   `crates/cordn-core/tests/db_cross_read.rs`, which opens a DB written by the
   TS `SqliteCoordinatorStorage` (`tests/fixtures/ts_written.db`, paired with
   its `ts_written.manifest.json`) and asserts every row — blobs, INTEGER
   booleans, NULL `join_after_cursor`, the `publication_event_json` column, and
   per-group cursor allocation — reads back byte-for-byte. The Rust test no
   longer asserts the legacy `encrypted` column (TS 0.5 dropped it; see the
   migration note below). The committed fixture is regenerated against TS 0.5+
   (the `group_messages.encrypted` column is gone); the generator script
   `references/cordn/scripts/gen_ts_db.test.ts` no longer inserts/selects it.
   Regenerate whenever the TS schema or write path changes:
   `npx vitest run scripts/gen_ts_db.test.ts` from `references/cordn`.

   **The generator scripts are untracked.**
   `references/cordn/scripts/gen_ts_db.test.ts` and `gen_key_packages.test.ts`
   are cordn-rs test infrastructure but are **not in this repo** — `references/`
   is gitignored (it holds clones of `cordn`, `openmls`, `rs-sdk`), and they are
   not committed upstream to `cordn-msg/cordn` either. They survive only in the
   local `references/cordn` working tree. Regenerating fixtures therefore needs
   a checkout of `cordn-msg/cordn` at `references/cordn` with these scripts
   present (they import the TS source + its `node_modules`). Losing
   `references/cordn` loses the scripts — back them up, or upstream them to
   `cordn-msg/cordn` if that fragility starts to hurt.

Commands:

```bash
cargo test                          # all tests, all crates
cargo test -p cordn-core            # core only
cargo test -p cordn-core storage    # filter by name substring
cargo test --test storage_parity    # a specific integration-test target
cargo test --test db_cross_read     # TS-written DB → Rust read (layer 4)
```

Test locations and naming:

- unit tests live inline (`#[cfg(test)]`) beside the code they test
- integration tests live under each crate's `tests/` directory
- parity test ports are named after their TS counterparts
  (`coordinator.test.ts` → `tests/coordinator.rs`, etc.)

When changing coordinator, server, or contract behavior, port or update the
corresponding TS test. When changing group-message streaming, cover backlog
replay and live delivery behavior.

## Code style

- Rust idioms; `cargo fmt` + `cargo clippy --all-targets -- -D warnings` must be
  clean before commit.
- Prefer small, direct modules over abstraction-heavy refactors (matches the TS
  style). No trait with one implementation, no speculative generics, no config
  for values that never change.
- Keep naming aligned with the domain concepts already used in
  `references/cordn/src/coordinator/types.ts` (snake_case in Rust, but preserve
  the conceptual names: `stable_pubkey`, `key_package_ref`, `after_cursor`, etc.).
- Wire/JSON field names in `contracts.rs` must match the TS wire schema exactly
  (`kp_ref`, `kp_64`, `welcome_64`, `gid`, `msg_64`, `after`, `at`, `pk`,
  `last_resort`, …) — these are cross-impl compatibility surfaces. Use
  `#[serde(rename = "...")]` where Rust naming diverges.
- Mark deliberate simplifications with a `// ponytail:` comment naming the
  shortcut and its upgrade path.

## Coordinator contract notes (must preserve)

These invariants come from the TS `AGENTS.md` and are load-bearing.

- **Group delivery cursors are monotonic per group, never global across all
  groups.** Different groups may each have a message with cursor 1.
- `fetch_group_messages({ group_id, after_cursor })` must treat `after_cursor`
  as a cursor within that group only.
- `fetch_many_group_messages` must preserve bounded catch-up semantics with
  independent per-group cursors.
- `subscribe_group_messages({ group_id, after_cursor })` (a coordinator-core
  method, **not** a wire tool — the single-group subscribe was dropped from
  the wire in cordn 0.5) is live-tail only; it does not replay backlog.
- `subscribe_many_group_messages` is the only subscription wire tool (cordn
  0.5 dropped the single-group `msg_sub`). It must remain
  backwards-compatible with the single-group subscription stream shape while
  preserving independent per-group cursor semantics, including the per-group
  "emit only if `cursor > last_emitted`" dedup that bridges backlog replay
  into the live stream.
- Observation (fetch) **never deletes**. Records are retired only by explicit
  `consumed` acks or the max-age ceiling.
- Keep storage backends behaviorally aligned: changes in `in_memory.rs` and
  `sqlite.rs` require parity coverage in the storage tests.
- **Pub/sub asymmetry (faithful to TS):** only
  `subscribe_many_group_messages` is exposed on the wire (cordn 0.5 dropped
  the single-group `msg_sub`). The coordinator-core
  `subscribe_group_messages` still exists as a live-tail-only primitive used
  internally (and by the TS CLI), but the adapter no longer wraps it: it does
  not replay backlog. `subscribe_many_group_messages` merges backlog+live
  into one stream with per-group cursor dedup, buffering any live messages
  that arrive during the backlog fetch and flushing them after the backlog so
  order is always backlog-then-live. The multi-group path fills the
  `mpsc::UnboundedReceiver` (via `GroupMessageSubscription::recv`) during
  setup.

## Storage / DB parity (the drop-in contract)

The SQLite schema is fixed and small. The authoritative definition is
`references/cordn/src/coordinator/storage/sqliteStorage.ts` — tables
`key_packages`, `welcomes`, `join_requests`, `group_messages`, `group_routing`.
Port it byte-for-byte, including:

- Per-group cursor allocation: `group_routing.last_message_cursor + 1`, never a
  table-global sequence.
- The migration logic that adds `join_after_cursor` and drops legacy
  `epoch`, `ephemeral_sender_pubkey`, `latest_handshake_epoch` columns when
  present on existing DBs (so we can read TS-written DBs). The TS 0.5
  encrypted-only refactor removed the `group_messages.encrypted` column; both
  backends now neither create nor drop it, and existing DBs that still carry
  it are ignored (all reads use an explicit column list that no longer names
  it).
- Refresh-in-place on join-request re-request: bump `created_at` and update
  `key_package_ref` for an existing `(group_id, requester_stable_pubkey)` so a
  re-request evades an admin's already-recorded consume ref.
- The per-group pending-join-request cap
  (`MAX_PENDING_JOIN_REQUESTS_PER_GROUP = 100`), enforced only on the insert path.
- Production pragmas on every connection: `journal_mode = WAL`,
  `foreign_keys = ON`, `busy_timeout = 5000`.

`key_package_bytes` / `welcome_bytes` / `opaque_message` are stored as the raw
incoming bytes (decision #2). A row written by TS stores ts-mls's re-encoded
bytes; since we never rewrite existing rows and MLS TLS encoding is canonical,
cross-reads are safe.

## Build and deployment

- `cargo build --release -p cordn-server` produces the optimized binary.
- Runtime configuration is environment-driven (see Development workflow).
- The server entrypoint prints a startup banner (pubkey, nprofile, relay list,
  cordn.net URL) to stdout, then structured logs. Shutdown on `SIGTERM`/`SIGINT`.
- **Releases and versioning.** The workspace `version` is the **TS-parity
  version** — it tracks `cordn` upstream and only moves when TS moves.
  - **Parity releases** (`make patch|minor|major` → `vX.Y.Z`): bump the cargo
    version to match a new `cordn` release. The only releases that change the
    binary version.
  - **Packaging-only releases** (Docker image, installer updates — no behavior
    change): tag `vX.Y.Z-<label>.N` (e.g. `v0.5.1-next.0`, `v0.5.1-rs.1`)
    **without** bumping the cargo version. The suffix is a release label, never
    a library version, so `cordn-server --version` still reports the parity
    version. It parses as a semver pre-release (lower precedence) — harmless,
    and it makes GitHub treat the tag as a prerelease, leaving the last clean
    `vX.Y.Z` as the "latest release."
  Both tag shapes match `release.yml`'s `v*` trigger and publish binaries + the
  multi-arch GHCR image; `:latest` follows the newest tag of either kind.

## Pull request guidelines

- Keep changes scoped and minimal; prefer the shortest diff that preserves the
  invariants above.
- Required checks before commit: `cargo fmt --all`, `cargo clippy --all-targets
  -- -D warnings`, `cargo test`.
- If you change external behavior, port/update the corresponding TS test and
  keep wire field names in `contracts.rs` byte-identical.
- If you change the SQLite schema or any storage write path, justify DB parity
  against the TS implementation explicitly.

## Troubleshooting

- Server fails at startup → check `CORDN_SERVER_PRIVATE_KEY` and `CORDN_RELAY_URLS`.
- A TS-written DB doesn't read → compare the schema and migration branches
  against `sqliteStorage.ts`; the divergence is almost always a column the TS
  migration adds or drops that we missed.
- Streaming tests hang → the backlog-replay-then-live handoff in
  `subscribe_many_group_messages` is the usual suspect; verify the per-group
  cursor dedup and that backlog is fetched *after* the live subscriber is
  registered (same ordering as the TS implementation).
